Steppewise

Steppewise — deterministic rails for agentic workflows. .NET 10 · Microsoft Agent Framework · OpenTelemetry. Every step verified, every decision human, every run a receipt.

This page follows one run of the bundled service-intake example from start to finish. Plain language comes first; open “Technical detail” under any step for the names you will see in the code.

The short version

What does it do?

It runs a fixed, five-step workflow: draft a result, check it, repair it, check it again, then stop and wait for a person.

What does the human decide?

Whether to accept or reject one exact, already-checked result. Nothing finishes as Accepted or Rejected without that decision.

What evidence remains?

A receipt: an append-only log of every step, both versions of the result, the check outcomes, and the decision with the fingerprint it applied to.

No AI is called. In v0.1.0 every “drafted” result comes from a deterministic synthetic fixture, so each run behaves the same way. The workflow shape is what is being demonstrated.

Step 1 of 7 · Automated

A change request arrives

You start a run of the service-intake example. Its input is a synthetic change request, ticket CR-1042. Steppewise gives the run an ID and writes its first entry to the run’s log before doing anything else.

Technical detail
  • Workflow definition: examples/service-intake.json, a five-step sequential chain checked by ValidateDefinition at startup.
  • The input travels as a RunInput sealed record through a Microsoft Agent Framework WorkflowBuilder graph.
  • Admission appends to run-<id>.events.jsonl and writes the first of up to three snapshots (run-<id>.json).

Step 2 of 7 · Automated

The workflow drafts a candidate

The draft step produces candidate-1, a change-request packet. In this release it comes from a fixed fixture, not a model.

Candidate
A proposed result that must pass verification and receive human acceptance before the run can finish as Accepted.
Hash (SHA-256)
A fingerprint computed from the candidate’s exact content. Change one character and the fingerprint changes, so it identifies one specific version.
candidate-1
ticket: "CR-1042"
rollbackPlan: (missing)
sha256: a41c…09e2 (example value)
Technical detail
  • Step action: fixture.draft. Execution boundary: evidenceMode: "fixture", liveInference: false.
  • The step emits a Candidate record carrying RunId, Sequence and CauseSequence.
  • Packet shown simplified. See the fixture for the full field list.

Step 3 of 7 · Automated check

Verification catches a missing rollback plan

An automated check reads candidate-1 and finds no rollback plan. The check records a failing verdict. Candidate-1 is not deleted; it stays in the log as evidence of what was caught.

Verification
An automated, rule-based check of a candidate. It produces a pass or fail verdict. It does not approve anything; only a person does that.

✕ Fail — candidate-1: rollbackPlan is missing

Technical detail
  • Step action: verify, which emits a Verdict record.
  • Candidate-1 and its SHA-256 digest are preserved in the ledger.

Step 4 of 7 · Automated

Repair produces a second candidate

The repair step produces candidate-2, which adds the rollback plan. Both versions stay available, each with its own fingerprint.

In v0.1.0, repair runs every time as part of the fixed sequence. It is not triggered by the failed check.

candidate-1 (kept)
rollbackPlan: (missing)
sha256: a41c…09e2
candidate-2 (new)
rollbackPlan: present
sha256: 7be3…5d10

Hash values on this page are examples, not real digests.

Technical detail
  • Step action: fixture.repair. Conditional branching is pending (M4).
  • Both candidates are preserved in the ledger with their SHA-256 digests.

Step 5 of 7 · Automated check

Verification checks the repaired candidate

The same check runs on candidate-2 and passes. The run then pauses in AwaitingReview. A passing check does not finish the run; it only makes the candidate eligible for a human decision.

✓ Pass — candidate-2 (sha256: 7be3…5d10)

Technical detail
  • Second verify step. The workflow reaches a RequestPort<Verdict, ReviewDecision> and waits.
  • Snapshot 2 of 3 is written at the waiting-review phase.
  • If the host restarts here, the pending review is rebuilt from the event log (RestoreReview), not resumed from a framework checkpoint.

Step 6 of 7 · Human decision

A person accepts or rejects that exact candidate

This is the workflow’s human decision step. You review candidate-2 and choose. Your decision is tied to candidate-2’s fingerprint, so it cannot be applied to a different version by mistake.

Reviewing candidate-2 · sha256 7be3…5d10 · check: ✓ Pass

No decision yet. The run is awaiting review.

The reviewer name is optional and self-reported. If left blank, the run records local-process-user. Neither is an authenticated identity.

Technical detail
  • POST /api/runs/{id}/review with expectedHash, which must equal the latest verified candidate’s SHA-256 hash.
  • A stale hash, a second decision, or a review against a failed run returns HTTP 409.
  • Attribution: actorSource: "self-reported", or local-process-user when omitted.

Step 7 of 7 · Automated

The run keeps a receipt

Run status: Awaiting review. In Steppewise, the events recorded so far are already on disk, because each step was written down before the next one started.

Receipt
The durable record of a run: what each step produced, what each check found, and what the person decided about which fingerprint. Entries are only ever added, never edited.
  • run-<id>.events.jsonl — the step-by-step log
  • run-<id>.json — a summary snapshot of the run’s current state
  • spans.jsonl — matching OpenTelemetry trace records
Technical detail
  • Each transition appends and flushes one DurableEvent JSONL record before advancing.
  • Snapshots are reductions of the log, written at admission, waiting review and terminal state.
  • traceId and spanId match between the event log and spans.jsonl. Spans are local files; OTLP network export is pending (M4).

Current limits (v0.1.0)

This is a reference implementation for learning and review, not a production system.

Show what this release does not do
  • Synthetic fixtures only. No live AI or LLM calls, no external network requests.
  • Repair always runs; there are no general conditions or parallel steps yet.
  • Loopback only (127.0.0.1), dev and qa profiles. prod is refused at startup.
  • Reviewer identity is self-reported or the OS process user. There is no authentication.
  • One host per evidence directory, enforced by .owner.lock. No distributed or multi-host execution.
  • A truncated event log stops the whole host at startup. Planned, not built: quarantining only the affected run.
  • Process-kill fault trials do not establish power-loss or multi-host durability.

Try it yourself

  1. Install the .NET 10 SDK (10.0.401 or newer 10.0.4xx).
  2. From the repository root, build and run: 
    dotnet restore src/Steppewise/Steppewise.csproj --locked-mode
dotnet build src/Steppewise/Steppewise.csproj -c Release --no-restore -warnaserror
./scripts/run.sh
    On Windows, use the PowerShell commands in the README Quick Start.
  3. Open http://127.0.0.1:5188, pick Service intake · change request review, and start a run.
  4. When it pauses, click Accept repaired result or Reject run. Switch to the Engineer view to see the hashes.
